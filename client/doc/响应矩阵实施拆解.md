# 阶段 1 响应矩阵实施拆解

## 当前代码事实

- 技术标主流程在 `src/features/technical-plan/pages/TechnicalPlanHome.tsx`，当前步骤是：选择标书、招标文件解析、目录生成、全局事实设定、生成正文、扩写改写。
- 前端状态类型在 `src/features/technical-plan/types.ts`，`TechnicalPlanState` 目前保存了解析结果、大纲、全局事实和正文状态，但没有独立的招标要求清单。
- 招标解析任务在 `electron/services/bidAnalysisTask.cjs`，已有可复用解析项：技术评分要求、交货和服务要求、采购清单、响应文件要求、资格性审查、符合性检查、评标要求、无效标与废标项。
- 解析结果落在 SQLite 表 `technical_plan_bid_items`，读取与保存逻辑在 `electron/services/technicalPlanStore.cjs`。
- 数据库当前版本是 `electron/services/sqliteDatabase.cjs` 的 `schemaVersion = 15`。
- 大纲节点表 `technical_plan_outline_nodes` 已有 `source_requirement_id` 和 `source_requirement_title` 两个字段，但目前只支持一个来源要求，不足以承载多个要求覆盖关系。
- 前端通过 `electron/preload.cjs` 暴露的 `window.yibiao.technicalPlan` 调用 IPC，IPC 注册点在 `electron/ipc/technicalPlanIpc.cjs`。

## 实施边界

阶段 1 只做“响应矩阵”，不同时做大纲覆盖自动回写。原因是覆盖关系属于阶段 2；阶段 1 先把要求清单稳定落库、可查看、可编辑、可刷新。

第一版采用“解析完成后手动生成/刷新矩阵”，不在每个解析任务完成时自动触发。这样更容易验收，也能避免模型或任务失败时反复覆盖用户手工备注。

## 数据库迁移

`electron/services/sqliteDatabase.cjs` 升级到 v16，新增表：

```sql
CREATE TABLE IF NOT EXISTS technical_plan_requirements (
  requirement_id TEXT PRIMARY KEY,
  requirement_type TEXT NOT NULL,
  title TEXT NOT NULL,
  original_text TEXT NOT NULL DEFAULT '',
  source_location TEXT NOT NULL DEFAULT '',
  importance TEXT NOT NULL DEFAULT 'medium',
  response_status TEXT NOT NULL DEFAULT 'unmapped',
  outline_node_ids_json TEXT NOT NULL DEFAULT '[]',
  evidence_notes TEXT NOT NULL DEFAULT '',
  risk_reason TEXT NOT NULL DEFAULT '',
  user_notes TEXT NOT NULL DEFAULT '',
  source_bid_item_ids_json TEXT NOT NULL DEFAULT '[]',
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_technical_plan_requirements_order
ON technical_plan_requirements(sort_order, requirement_id);

CREATE INDEX IF NOT EXISTS idx_technical_plan_requirements_status
ON technical_plan_requirements(response_status, importance);
```

`schemaHealthTableGroups` 也要加入 `technical_plan_requirements`，保证旧库被健康检查自动修复。

## 矩阵生成策略

第一版从已解析结果归并，不重读全文：

| 解析项 | requirementType | importance |
| --- | --- | --- |
| `techRequirements` | `scoring` / `technical` | `high` / `medium` |
| `deliveryAndServiceRequirements` | `delivery` / `service` / `acceptance` | `high` |
| `procurementList` | `technical` | `high` |
| `responseFileRequirements` | `mandatory` | `high` |
| `qualificationReview` | `qualification` | `high` |
| `complianceCheck` | `mandatory` | `high` |
| `evaluationBid` | `scoring` / `mandatory` | `medium` |
| `discardedBids` | `rejection` | `high` |
| `businessScoring` | `business` | `low` |

生成方式：

1. 收集 `technical_plan_bid_items` 中 `status = success` 且内容非空的解析项。
2. 用一个独立 prompt 要求模型输出 JSON 数组。
3. 程序校验字段、补 ID、限制枚举值、截断过长标题。
4. 写入 SQLite。
5. 保留已有同 ID 或同标题的 `userNotes` 和 `responseStatus`，避免用户编辑丢失。

第一版 ID 建议用稳定哈希：

```text
req_${sha1(requirementType + title + originalText).slice(0, 12)}
```

优先改 `src/features/technical-plan/pages/BidAnalysisPage.tsx`，不要新开顶层步骤。阶段 1 的 UI 形态：

- 生成后：显示数量和高风险未覆盖数量。

## 验收清单

阶段 1 可验收条件：

- 完整解析招标文件后，能手动生成一张响应矩阵。
- 矩阵里能区分技术评分项、强制响应项、资格/符合性项、废标风险项。
- 用户能修改某条要求的状态和备注。
- 刷新页面后矩阵数据仍保留。
- 清空技术方案后矩阵也被清空。
- 不会因为重新打开应用而丢失用户备注。

## 风险点

- AI 归并可能漏项，所以第一版必须保留原始解析结果入口。
- 来源位置不承诺精确页码，只保存章节、条款、表格等线索。
- 不允许模型静默删除用户已编辑条目。
- 高风险条目默认不能自动忽略，只能由用户手动改状态。
